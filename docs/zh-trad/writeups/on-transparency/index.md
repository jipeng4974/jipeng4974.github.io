# 論透明度

> 透明度，或者說程序的白盒指數，是互聯網軟件工程實踐中長期被忽略的一個理想屬性。

---

LLMS index: [llms.txt](/llms.txt)

---

透明度是軟件工程中長期被忽略的理想屬性，是目前互聯網行業技術管理體系中的薄弱環節。本文的透明度主要是指組件內部實現對研發團隊的可見度、可解釋性和可掌控程度，或者說[白盒](https://en.wikipedia.org/wiki/White_box_(software_engineering))指數。

一個項目自上而下依賴的第三方黑盒越少，各個抽象層次上諸多組件對研發團隊就越是透明的。高透明度意味着高度可維護，高度hackable，隨時可拆卸，定位到任何抽象層次上存在性能瓶頸都能毫無桎梏地zoom in，然後修改、重構。習慣性地使用第三方依賴，哪怕這個依賴是得到廣泛應用，甚至接近行業標準的高聲望項目，依然會注入實現需求不完全匹配的風險。

高性能計算的一個重要啓發式設計原則(heuristic)即特化(specialization)，特化顯然包括軟件特化——基於新的真實需求創造最直接貼合需求的新解決方案(direct solutions to the needs)，即造輪。

國內互聯網同行們對造輪持過分謹慎態度，將其視爲anti-pattern，遇到問題時立刻開始技術選型，對使用第三方依賴形成了不假思索的路徑依賴。缺乏洞察問題的新穎性和獨特性的敏銳度和飢渴，自然故步自封於技術選型，而無法做到真正的技術創新——計算系統的創新是根植於真實需求，對非結構化的現實需求施加結構，創造新的計算和存儲形態。就以全文檢索爲例，[美團外賣搜索用ES](https://tech.meituan.com/2022/11/17/elasicsearch-optimization-practice-based-on-run-length-encoding.html)，[微信聊天搜索用SQLite](https://zhuanlan.zhihu.com/p/608082104)，都是沒有選擇自研高性能檢索引擎，導致業務場景和經典解決方案出現錯配，後期遇到了性能瓶頸後的所謂優化方案也只不過是對第三方庫進行魔改，讓它更貼合原本的需求罷了。比如lucene壓根就不是in-memory索引，以至於外賣店家商品搜索這麼小規模的場景都不能保證實時性。再說SQLite，默認當然不支持拆表+並行搜索，針對大庫做簡單的拆表和scatter-gather並行搜索提升性能其實是理所當然的解決方案。

如此視造輪爲畏途實讓人唏噓，在性能上碰壁後，再鑽進別人的故紙堆中修修補補，浪費的精力，產生額外的痛苦，遠遠超過當初用C++/Rust實現一個小而美的in-memory search index(例如[pisa](https://github.com/pisa-engine/pisa))。自研檢索引擎用極少的代碼量就可以擊敗lucene、sqlite、postgres，也可以很輕鬆地支持多線程實時索引更新，而不必犧牲索引性能，還可以針對現代物理機進行深度cache優化、減少核間通信和遠端內存訪問，將現代硬件的性能在檢索這種訪存密集應用上發揮到極致。
