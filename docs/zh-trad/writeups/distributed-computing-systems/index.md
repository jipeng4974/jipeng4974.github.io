# Distributed Computing Systems At Scale
分佈式計算系統完成規模化的跳躍後，核心挑戰是正確性和系統效率。前者對應共識抽象，後者對應性能工程。

## Consensus Abstraction
分佈式系統的正確性實際上蘊含了穩定性、一致性、可用性等理想屬性。
分佈式天然意味着併發執行、進程失敗、不可靠的消息傳輸，這些因素都使正確性在各種常見的分佈式應用語境下變得極爲困難：
- 併發意味着執行軌跡空間維度爆炸，和(進程數*步數)的階乘成正比。很難保證每個執行路徑都是對的。
- 進程失敗可分爲：崩潰（進程沒了，網卡或CPU故障）、丟請求（沒崩，網絡阻塞或服務降級導致臨時不可用）、恢復後崩潰（反覆重啓，最終恢復到正確狀態，往往基於日誌）、拜占庭失敗（不可預料，來自宇宙射線或惡意攻擊）。
- 消息傳輸面臨篡改、丟包、重傳、亂序等風險，即使是可靠網絡協議也不完全可靠。

共識是指多個進程就某個問題（2-general問題、複製狀態機保證全局序的問題、分佈式事務）最終形成一致決定。理想的共識算法應具備安全性(safety)和活性(liveliness)。安全性包括validity（只有一個提議值被選擇）、agreement（正確的節點保持一致）、integrity（每個節點最多選一次）。活性則是指可終止，每個正確節點最終總會選擇一個值，而不是hang住。

如果不考慮安全性的話，TCP其實就是一個最簡單、粗糙、有效的共識協議，TCP協議本質是讓通信的兩個進程對連接的狀態達成了共識，才能可靠地通信。比如進程關閉連接，就會把本地狀態改爲TIME_WAIT，等幾分鐘後才真正釋放資源，以確保對方收到ACK，用簡單的等待，達成高概率的共識，避免雙方開始下一輪連接後收到舊報文而出錯。

如果追求完全安全，簡單的場景是隻對一個值進行商議和決策，即單值共識。

單值共識前提下的最簡場景則是擁有完美失敗檢測能力，泛洪共識（只有獲得所有進程提議才做出決定）、等級統一共識就是這種場景下的簡單解決方案。

若只具備最終失敗檢測能力，則需引入代次變更概念，用代次共識（往往是Paxos變種）去解決。Paxos是唯一已知的completely-safe & largely-live的容錯共識算法。2PC其實也是一種代次共識，不過2PC裏協調者宕機就會全局阻塞，是safe but not live的典型。Paxos甚至可以通過將代次(round)的偏序關係從<改成整除，來實現多維的先後代次，從而兼具2PC的功能。

如果再把單值共識推廣到序列共識（在分佈式存儲中更常用，因爲log-structured store的寫操作是一個append-only序列，而非單值），則從Paxos進化爲某種Multi-Paxos，或Raft。Raft本質上解決了複製狀態機問題，而序列共識問題恰好可以歸約爲複製狀態機問題。

如果再考慮拜占庭失敗，則需BFT、PBFT、PoW。

## Performance Engineering
性能的重要性毋庸置疑，端上應用（語音識別、智能客服）的延遲夠不夠低直接決定項目是否成立，而大規模的IDC應用(搜廣推、存儲、在線推理、訓練)的吞吐性能則直接和金錢與環保掛鉤。

計算系統的性能與分佈式密不可分。因爲幾乎所有計算系統都是分佈式的，包括單機，單卡，單設備，因爲單機（in-node）仍然有網絡結構，比如NVLink和NVSwitch，甚至Xeon CPU都是衆核通過總線連起來的，網卡、SSD等設備，拆開來看都是網聯設備（networked device）。通過分區、並行、軟硬件協同、減少不必要的分層獲取性能的方法是普適的。

如果存在基線，性能工程的主要工作就是優化、迭代，和漸進式創新。
當基線不夠好時，性能工程(performance engineering)是發散的：跨越層次的，不同抽象層次、不同的模塊都有可能成爲瓶頸，不應存在優化盲點，必要時還需反分層，比如將整個IO路徑放到用戶態，比如暴露hypervisor狀態給vm以便高效調度。
當基線已經非常好時，性能路徑(performance path)則是收斂的：明確指向軟硬件協同，畢竟性能最終來源於對硬件資源的量體裁衣和極限壓榨，如果協同也足夠好，那就只能指向硬件更新：更大更強的N卡、TPUv4這樣的DSA、OCS這樣的光學路由以及更進一步的AI DC建設。

如果是全新的問題，或對已有問題產生了非凡洞察，對其施加更有效結構，就產生了新的架構，新的計算和IO形態：
- 大模型時代來臨後，模型參數本身就已經放不進頂級的GPU，更不用說神經網絡計算所需的額外內存了，這就使原本在系統效率和正確性之間平衡的非常好的Parameter Server架構面臨挑戰，不得不用全新的架構和策略解決大模型訓練的問題：Node內（8卡組一個Node）的權重切分和模型並行，算子內的數據和指令並行，子圖切分、算子擺佈和流水線並行（8個Node做8級流水）、16組8*8做Batch16的數據並行，於是產生了Alpa over Ray訓練大模型的解決方案。這又間接導致帶寬需求激增，以至於需要Google的光學交換機OCS這樣的網絡解決方案，避免光電模塊和解析報文計算的開銷——光交換劣勢在於切換慢，但訓練週期裏數據交換的主要流量路由是固定的，用來建設AI DC正好規避了這個缺點。
- KVM的作者根據hypervisor在NUMA系統上的性能瓶頸的經驗，很容易就發現應用層共享內存的並行模型是有缺陷的，在衆核時代尤其嚴重，因此創造了seastar。利用hardware locality，避免線程切換、數據拷貝、NUMA遠端內存訪問，對訪存密集型CPU-bound應用來說，是非常重要的性能路徑。
