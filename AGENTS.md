photos section pages use progressive image loading: layouts/_markup/render-image.html wraps every image of each photos page in placeholder frames, assets/js/photo-gallery.js (injected via layouts/_partials/hooks/body-end.html) fetches them on scroll with a concurrency cap, streamed download progress and retries, and adds a fullscreen lightbox (click to open, prev/next arrows, ESC/X/backdrop to close, live progress for pending photos); styles live in assets/scss/_styles_project.scss

photos section pages also have a rectangular thumbnail guide above the originals: layouts/_partials/photo-guide.html emits ordered photo URLs plus dimensions from generated data/photo_metrics.toml, and assets/js/photo-guide.js deterministically partitions the photos into variable-height mosaic rows; clicking a tile scrolls to its corresponding progressive-loading frame. Guide thumbnails load eagerly and photo-guide.js exposes photoGuideReady; photo-gallery.js waits for that promise before starting original downloads. Thumbnails are expected at https://assets.wujipeng.com/thumbs/<stem>.jpg. After adding/changing photos, prepare the local thumbnail manifest and run scripts/generate-photo-metrics.py.

Photo presentation is decided by the viewport at runtime (no configuration): portrait-aspect screens (phones) get the legacy tiled `mosaic` flow, everything else gets `stacked` — OpenAI-style sticky cards inside one shared tall scroll group (photo-guide.js applies `photo-mode-stacked`/`photo-mode-mosaic` on `.td-content`). Thumbnail jumps target invisible stack anchors and prioritize the target original.

Writeup articles carry a hairline reading-progress line (assets/js/reading-progress.js, injected via layouts/_partials/hooks/body-end.html for the writeups section only, styled by `.td-read-progress` in assets/scss/_styles_project.scss). It rides whichever edge the shell already draws: vertical along the sidebar's right edge in landscape, horizontal along the subnav's bottom edge in portrait (the media query flips the axis, and the sidebar offset is measured with a ResizeObserver so the resizer and collapsed state come along for free). Progress is published as a 0–1 custom property `--td-read-progress`, which the gradient fill consumes as a `scale` and the spark as a `calc()` position — the scroll handler never touches geometry. Its ink is theme-scoped: light mode draws it in orange-red — a warm vermilion-orange body `#e25822`, a pale warm `#ffe0cf` spark core and a short 5px/80% halo — while dark mode keeps the shell blue, which on #111 already looks like a phosphor trace. It only exists on `body.td-page.td-blog` (writeup articles, not the section index, photo galleries or tag pages), fades in after 80px and out at the end, hides for print and stops its pulse under `prefers-reduced-motion`, and keeps z-index 23 so the phone sheet (25) and its backdrop (24) cover it.

Every page ends with its section's seal: scripts/make-seal.py renders the plate (seal-script font, thick strokes, a multi-octave noise field that eats the rims, chips the border and pinholes the ink), and layouts/_partials/section-seal.html stamps it bottom-right, linking back to the section index — writeups 時俗工巧, photos 鴻爪雪泥, gears 藏器於身, works 遊戲三昧. It is inserted before the pager in layouts/blog/_td-content.html and after the content in layouts/_td-content.html (the docs-type single pages: photos/gears/works), so it only appears on detail pages, never on section lists. The generator also takes --from-image, which weathers an already-rendered plate (a hand-drawn or generated one) instead of setting type: it flood-fills the paper from the corners to separate the plate from the background — necessary because those sources draw white characters on white paper — then runs the same weathering. The generated PNGs live in static/img/seals/ and are transparent where the characters are, which is what makes the 白文 (intaglio) effect follow whatever background they sit on. Two traps in the generator: --thicken is quoted relative to a 1200px seal, not scaled by work/size (scaling it silently multiplied the stroke weight by 6.7x at small output sizes and welded the glyphs together), and rough_edge's blur must stay well under half the stroke width or the threshold step erases the strokes instead of roughening them. The 中山王篆 font lacks 時鴻遊戲昧: the first four fall back to their simplified code points (same glyph), and 昧 is assembled from 日 + 未.

Diagrams in writeups are written as ```mermaid blocks — no configuration needed. Hugo itself has no mermaid support, but the Oink theme ships the whole path: layouts/_markup/render-codeblock-mermaid.html turns the block into `<pre class="mermaid">` and sets the `hasmermaid` page flag, then layouts/_partials/scripts.html loads layouts/_partials/scripts/mermaid.html, which serves the self-hosted assets/third_party/mermaid/mermaid.min.js, forces `theme: 'dark'` when the page is dark, and reloads on theme switch (mermaid cannot re-initialise). Multi-line ASCII art becomes `flowchart TD` with quoted labels (`A["Denoised AE"] --> B["VAE"]`); one-line arrow chains carrying footnote references stay as text, because footnote links do not survive inside a mermaid label. assets/scss/_styles_project.scss centres the SVG (`.td-content pre.mermaid { text-align: center }`) — mermaid sizes it to its own content, so a narrow vertical chain would otherwise hug the left edge. Light mode also overrides mermaid's palette under `[data-bs-theme='light']`: nodes take `--bs-body-bg` with plain black borders and connectors, the block background and edge-label backgrounds go transparent, so the diagram reads as a line drawing on the paper instead of lavender chips on a grey wash; dark mode keeps mermaid's own dark theme. Those rules need `!important` because mermaid injects its own as `#mermaid-<id> .node rect { … }` id selectors.

Writeup article pages open with one meta line instead of the theme's byline + "Tags:" blocks: layouts/blog/_td-content.html renders `<header class="article-meta article-meta-row">` with the date (en `Aug. 14, 2026`, zh `2026年8月14日`; both list cards and article pages format with `time_format_blog`), the tag chips, the light italic AI-assisted note (normal weight, 0.55 opacity) and the length + reading-time label (`Brief · 3 min read`, zh `短札 · 约 3 分钟`) last, and assets/scss/_styles_project.scss sizes the whole row from `--article-meta-band` plus a `--article-meta-font-size` of 0.75rem, so the date, chips, AI note and length label share one type size and the chips sit on the date's baseline — resetting the theme's `.td-content ul li` bottom margin is required for that, otherwise the chips float 4px high. The length label comes from layouts/_partials/article-length.html, which counts CJK ideographs + Latin word tokens in `.RawContent` (Latin: <800 Brief, <2000 Regular, else Long-form; CJK: <1200/<3000, a 1.5× density factor) and derives the reading time from the same count (Latin 220 or CJK 300 units/min, rounded up, minimum 1 minute; posts tagged `Math` multiply that rounded time by 3, while the tier stays based on the unweighted units; label format from the `article_length_with_time` i18n key); `.article-length` styles it as a system-only old-style serif in bold, adds Chinese-only generated `「」` brackets (`html[lang^='zh']`; English labels stay plain), and gives it `margin-inline-start: auto` so it flushes right after the chips, keeping the label on its own right-aligned line if the row wraps. The thresholds, reading speeds, Math weight and minute rounding are local to that partial. Chips carry no "Tags:" label, their hue comes from `hash.FNV32a` of the tag name (collisions nudged to the next free slot) mapped onto the cool `.article-tag--t0..t7` ramp, and the pointed left tip is an absolutely positioned `clip-path` triangle while the shadow is a `drop-shadow` on the `<li>` (box-shadow would miss the tip). The zh AI note reads its string from i18n/zh-cn.yaml, not zh.yaml: the zh site's locale (zh-CN) selects the regional i18n file.

Page headings in writeups/works/photos/about/gears place the description next to the h1 as a one- or two-line deck (layouts/_partials/page-heading-desc-fit.html decides, `.td-page-heading` in assets/scss/_styles_project.scss renders): the description box flexes from 22em up to 34em, and when the row cannot hold even 22em it wraps under the title with a row-gap (same shape as block mode). Inline vs block comes from measured text widths — title 12.8px per Latin char / 28px per CJK char (Georgia 28px bold), description 6.7 / 16 (Georgia 16px) — against a 940px row budget (the 1050px article max-width minus its 2 × 48px padding); a description needing more than two lines of the box it can actually get goes to block mode, so keep those constants in sync with the CSS if either width changes.

Writeup article first body paragraphs get a two-line drop cap via assets/js/dropcap.js (injected by layouts/_partials/hooks/body-end.html for the writeups section): it scans the first direct `.td-content > p`, picks the first Han character on Chinese pages or the first letter on English pages (skipping code/KaTeX; leading punctuation is included, while a leading number blocks the drop cap instead of reordering the paragraph), wraps the range in `.td-dropcap` (`.td-dropcap--latin` for Latin initials), and assets/scss/_styles_project.scss floats that span two body lines. Styling: English initials keep the red Palatino/Iowan/P052 serif; Chinese Han drop caps randomise per page load over muted traditional inks (`#b3261e` cinnabar plus ochre, rouge, dark crimson, rosewood, mineral blue/green, dai gray-blue, violet and ink black) and six face classes (`--kai`, `--song`, `--hei`, `--light`, `--black`, `--mono`, which degrade to the Noto CJK families on Linux), plus a small random size scale; the script stores the last face/ink index in `sessionStorage` so the next refresh usually differs. `.td-dropcap` consumes `--td-dropcap-ink` and `--td-dropcap-scale`, and dark mode lightens the ink with `color-mix`. Because the script checks `body.td-page.td-blog`, it only affects writeup single pages, never lists, tag pages, or other sections. There is no bundled Chinese display webfont, so Chinese falls back to the system calligraphic/serif stack; a guaranteed calligraphic face would need a multi-megabyte CJK webfont.

Breadcrumbs are disabled globally (`params.ui.breadcrumb_disable: true` in hugo.yml) — the site is shallow, and the sidebar/topbar already provide location context. Theme baseofs and the custom homepage all check that param, so no `.td-breadcrumbs` markup is emitted.

The shell treats `data-bs-theme` as a multi-value color mode, not just light/dark: `light` uses the flat `--bs-body-bg`; `classic` (古韵) reuses the light tokens plus the ×1.00 Paper001 texture (`static/textures/paper001-512.jpg`, CC0, ambientCG) on `body` and a milky white-jade Onyx015 wash (`static/textures/white-jade-512.jpg`, CC0, cooled to remove the paper-yellow cast) on the sidebar panel, portrait `.td-shell-subnav` topbar and `.td-shell-footline`; the portrait contents sheet opened from that topbar gets a translucent jade wash from `white-jade-soft.png`; the `.td-content .highlight` code surface paints the same jade layers (nested pre/chroma transparent, inline code falls back to the solid `--td-pre-bg: #f3f6f3`); `dark` keeps the theme's dark palette. In classic the root switcher trigger is transparent so its default state reads as the same jade rail (hover/expanded keep the neutral accent), and the popover uses a cool ivory card. assets/js/color-modes.js intercepts clicks on `[data-td-theme-toggle]` in the capture phase so the theme's binary dark-mode.js listener never sees them, cycles light → classic → dark, and stores the choice under the original `td-color-theme` key that the theme prepaint script already restores before first paint. The toggle glyph shows the target: light paints a tea cup (`td-shell-icon--tea`), classic paints 月亮 (`--moon`), dark paints 太阳 (`--sun`).
