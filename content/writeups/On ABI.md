A note up front: in this post, ABI refers specifically to the ABI of system languages. By system languages — i.e., system programming languages — I mean compiled languages used for systems programming, such as C, C++, and Rust. We sometimes also discuss the ABI of commonly used libraries or foundational libraries; for instance, GCC 5 changed the implementations of std::basic_string and std::list, which naturally affected ABI compatibility across versions. That kind of ABI compatibility is also an engineering headache, but it is out of scope for this post — after all, the source code itself differs. What this post discusses is the ABI compatibility of the binary artifacts produced from the same source code on different ISAs, operating systems, and compilers.

The ABI of system languages, the API of application-layer software, and the ISA of microprocessor architectures are all interfaces that describe the interoperability of their respective abstraction layers.

What makes the ABI unique is that it is itself a heavy implementation of mechanisms rather than a lightweight protocol declaration — there is a conceptual distinction between implementation and declaration, and this distinction has already manifested itself in law: copying an ABI is outright plagiarism, while copying an API or an ISA counts as fair use. You can obviously and legally write books annotating APIs or ISAs created by others; when Google implemented its own Java, it legally copied Oracle's Java API without needing a license.

The reason the ABI is complex is precisely that it sits between two abstraction layers. A large part of the ABI is accountable upward to the language standard and downward to the ISA; it must obey constraints from both directions and keep the complexity for itself, thereby enabling the two abstract contracts — the language standard and the ISA — to remain simple, clean, and human-friendly.

Calling conventions, one of the ABI's key components, are constrained by the ISA: i386 uses cdecl, stdcall, fastcall, vectorcall, and thiscall; amd64 uses systemv, msnative, and vectorcall; arm32 uses aapcs; arm64 uses aapcs64. A large part of the ABI is also instruction-set independent (ISA-agnostic), such as name mangling and class layout. These mechanisms are usually low-level enough and strongly coupled with the instruction-set-dependent parts, and combined with historical factors, only a small portion of them ever gets written into language standards.

If ISAs differ enough, maintaining different ABIs is undoubtedly necessary; forcing a single ABI to cover them all is neither natural nor efficient. Take early Windows as an example: Microsoft provided two ABIs, one for the earlier i386 (IA-32) and another for the later Intel IA-64. Later on, AMD won the 64-bit war, and Intel also adopted amd64 — backward-compatible with IA-32 — also known as x86_64 or x64, and IA-64 faded away.

Using the instructions, registers, and memory-management capabilities provided by the ISA as building blocks, the ABI describes, exhaustively and precisely, how to implement a system language's execution model on specific hardware, operating system, and compiler, and it allows separately compiled artifacts to interoperate. For example, the C ABI must define the calling convention, the representation of fundamental data types, and the memory layout of aggregate data types; the C++03 ABI must additionally define the exception mechanism, RTTI information storage, vtable layout and the dynamic dispatch mechanism, and the name mangling required for overloaded functions/operators and template instantiations; the C++11 ABI must further define the implementation of lambdas, automatic type deduction, and other newly introduced language mechanisms.

Neither C nor C++ has an official ABI standard at the language level — after all, an ABI standard itself restricts implementation freedom. The currently dominant Itanium C++ ABI claims to be adopted by many operating systems, adaptable to most microprocessor architectures, and implemented by most compilers, including the two major players, GCC and Clang. But it is worth noting that being supported by many parties does not mean those parties support exactly the same thing. Both flying the Itanium ABI flag, can a C++ library compiled by Clang on arm32 Linux be used by a program on amd64 Windows? Obviously not, because the most basic calling convention — and even the representation of fundamental data types — differs. Even if the Itanium C++ ABI achieved complete unification, its positive significance would be limited to making certain dangerous tricks that rely on CPU-independent rules (such as modifying vtables — operations we can only call hacks today) work across a fair number of environments. As long as the C++ language standard refuses to bring the ABI into its scope, techniques that make assumptions about the ABI will always be dangerous; to create new language mechanisms, some ABI consensus must first be advanced at the C++ standard level.

So should a system language standardize language features built on a particular ABI implementation? Judging from the history of C++, there is precedent for this — and it was rather reckless. Introducing dynamic exceptions and RTTI, both carrying non-zero abstraction overhead, into C++ objectively split the community: a considerable portion of C++ users still choose -fno-exceptions or -fno-rtti to this day. A recent proposal, [Zero-Overhead Deterministic Exceptions: Catching Values](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2021/p2232r0.html), presents a zero-overhead exception mechanism that changes the exception ABI — a belated fix for a historical mistake. A system language's standard should prudently standardize only ISA-agnostic ABI rules with zero abstraction overhead, so as to build new language mechanisms on top of them or to make application-layer development more convenient.
